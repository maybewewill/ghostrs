# ЗАДАЧА v2: Full Rejoin (как в Dota 2) для Warcraft III 1.26a

> Проверенная постановка. Все адреса/байты ниже верифицированы дизасмом `game.dll`
> (PE, imagebase 0x6F000000 подтверждён) и по коду ghostrs. Версия v1 имела 2
> неточных адреса, 1 опасный патч-рецепт и 1 противоречие — здесь исправлены.

## КОНТЕКСТ

- ghostrs — бот-хост WC3 для iCCup, Rust. Крейты: spectre, spectre-bnet, spectre-engine,
  spectre-net, spectre-protocol, spectre-spectator, spectre-store, spectre-loadtest.
- IDB для реверса: `D:\rewar3\game.dll.i64` (game.dll 1.26a, base 0x6F000000).
  MCP: `idb_open` с `input_path: "D:\\rewar3\\game.dll"`.
- **Fallback, если MCP недоступен (обрезает параметры):** скрипты в `.tmp_ida_verify/`
  (python 3.14 + capstone 5.0.7, самодостаточные: PE-парсер → VA→offset → дизасм).
  `verify.py` — патч-сайты и вызовы тик-цикла; `verify2/3/4.py` — контексты лимитеров,
  fourcc-проверки, IAT. Можно и нужно дописывать свои по тому же шаблону.
- Материал прошлой сессии: DotaTV .mix `D:\rep\iccup_replay_fix.cpp` — там НЕТ патчей
  скорости (проверено grep'ом: ни 0x553626, ни 0x22B4). Патчи скорости пишем с нуля.

## ЧТО ДОЛЖНО РАБОТАТЬ (цель)

Игрок вылетел (краш/ребут/закрыл war3.exe). ghostrs держит слот 180 сек
(`cfg.reconnect_wait`). Игрок перезапускает war3.exe с нашим .dll → тот читает
локальный токен-файл → подключается к ghostrs → загружает карту КАК ОБЫЧНЫЙ
МУЛЬТИПЛЕЕР-КЛИЕНТ (не реплей) → получает ВСЮ историю тёрнов 0..N → за лоадинг-
скрином проматывает их (патчи скорости) → управляет героем вживую.

Физический предел скорости catch-up: lockstep-симуляция однопоточная и
детерминистичная — клиент обязан выполнить все 144k тёрнов за 60 минут игры.
Реалистично: 4–15s на 30 мин игры, 7–30s на 60 мин (CPU-bound, замер см. этап 4).
Быстрее только перенос состояния — нереалистично (сервер не симулирует; см. риски).

### A.1 Сервер (по коду ghostrs)

### A.2 Клиент (по байтам game.dll, base 0x6F000000)

Главный тик-цикл `sub_6F553470`. Ключевые поля `CNetSession` (esi):

- `[esi+0x2250]` — аккумулятор времени (ms); `[esi+0x284]` — долг тёрнов;
  тик = **25ms** (`mov eax,0x19; cmp [esi+0x2250],eax` @ `0x6F553665-6A`) →
  4000ms cap = 160 тёрнов/кадр — арифметика v1 верна.
- Скорость: `mov eax,[esi+0x22B4]; imul eax,ebx(elapsed); div [esi+0x22B8];
  add [esi+0x2250],eax` @ `0x6F553604..19`, гейт `[esi+0x22BC]==0`.
  **`+0x22B4`=SPEED_NUM, `+0x22B8`=SPEED_DEN — подтверждено.**
  ⚠️ Следствие: НЕ трогая NUM/DEN, catch-up идёт со «живой» скоростью
  (acc растёт только на реальное elapsed). Для промотки NUM обязан быть большим.
- `sub_6F553440` — загрузчик следующего тёрна, вызов @ `0x6F55368A`. ✅
- `sub_6F54D930` FlushCommandBuffer: `mov eax,[ecx+0x2288]; cmp eax,'LOOP'
  (0x4C4F4F50); je; cmp eax,'NONE'(0x4E4F4E45); je` → иначе виртуальный вызов
  провайдера через `[ecx+0x1C78]`. ✅ Ровно как в v1.
- `sub_6F53E670` IsMultiplayerGame: provider != 'LOOP' && != 'NONE' → 1. ✅
- `sub_6F537D20` SetReplayState: читает/пишет `+0x614`. ✅
- `sub_6F53E0B0` SetGameState: читает/пишет `+0x270`. ✅ (в тике вызывается с 6 @ `0x6F5537C2`)
- `dword_6FAB65F4` — .data/BSS, инициализируется в рантайме, **1346 ссылок** imm32
  по .text — живой глобал (заявка «CGameUI*» правдоподобна, тип не верифицирован).
- Путь к CNetSession из любого хука (пролог `sub_6F53F160`, верифицирован):
  `mov ecx,0xD; call 0x6F4C34D0; mov eax,[eax+0x10]; mov ecx,[eax+8]` → CNetSession*.
- Таблица слотов: stride **0x304** от `+0x278`, состояние слота `>= 3` = playing
  (из `sub_6F54D970` NetSendCommandStore: `cmp edi,[esi+0x610]; imul ecx,ecx,0x304;
  cmp [ecx+esi+0x278],3`).

## B. КРИТИЧЕСКИЕ ИСПРАВЛЕНИЯ ПРОТИВ v1 (читать обязательно)

### B.1 Точная таблица патчей (байт-в-байт)

Адреса v1 были сдвинуты на ≤5 байт (указывали на `jb/je` ПОСЛЕ cmp). Точные байты:

| # | Что | Адрес | Старые байты | Новые байты |
|---|-----|-------|--------------|-------------|
| P1 | Лимитер A: `cmp eax,0xFA0` (imm) | `0x6F553622` | `A0 0F 00 00` | `20 4E 00 00` (20000ms = 800 тёрнов/кадр) |
| P2 | Лимитер A: кламп `mov eax,0xFA0` (imm) | `0x6F553629` | `A0 0F 00 00` | `20 4E 00 00` |
| P3 | Антифриз: сброс acc `mov [esi+0x2250],edi` — **NOP целиком** | `0x6F5537E5` | `89 BE 50 22 00 00` | `90 90 90 90 90 90` |
| P3' | (альтернатива P3) imm `cmp eax,0xC8` | `0x6F5537DF` | `C8 00 00 00` | `FF FF FF FF` |

Контекст (для самопроверки в IDA):
- `0x6F553621: 3D A0 0F 00 00  cmp eax,0xFA0` → `0x6F553626: 72 05 jb` →
  `0x6F553628: B8 A0 0F 00 00  mov eax,0xFA0` → `0x6F55362D: mov edx,[esi+0x22A8]` →
  `0x6F553633: mov [esi+0x2250],eax` (сохранение клампнутого acc).
- `0x6F5537D5: call 0x6F6C4E00` (таймер, jmp-танк → `[0x6F86D230]`) →
  `0x6F5537DA: sub eax,[esp+0x18]` → `0x6F5537DE: cmp eax,0xC8` →
  `0x6F5537E3: jbe` → `0x6F5537E5: сброс acc` → `0x6F5537EB: mov eax,0x19` (хвост цикла).

### B.2 ЗАПРЕЩЕНО (ошибка v1)

- ❌ **NOP условного прыжка `jbe` @ `0x6F5537E3`** — прыжок перепрыгивает СБРОС acc;
  NOP-нуть его = сброс будет выполняться ВСЕГДА, промотка умрёт. Только P3/P3'.
- ❌ Не трогать `jb` @ `0x6F553626` (часть логики клампа).
- ❌ Не писать `+0x610` вручную (см. B.4).
- ❌ Не ставить cap в бесконечность: один кадр на 15+ секунд заморозит памп окна
  («Не отвечает»). 20000ms = 800 тёрнов/кадр достаточно: без рендера кадров сотни/с.

### B.3 SPEED_NUM/DEN: план промотки

1. До catch-up: сохранить `[esi+0x22B4]`/`[esi+0x22B8]`; записать NUM=99999
   (байты `9F 86 01 00`), DEN=1 (`01 00 00 00`).
2. acc тогда насыщает cap каждый кадр → 800 тёрнов/кадр; упираемся в CPU симуляции.
3. После catch-up: **обязательно вернуть NUM=1/DEN=1** (иначе живая игра пойдёт
   с нулевым сетевым буфером → микрофризы).
4. Антифриз при NUM>1 активен всегда → P3 обязателен. (Гейт NUM>1: флаг из
   `sbb ebx,ebx; neg ebx` @ `0x6F553648-4A`; НО ebx перезаписывается в теле цикла
   `lea ebx,[esi+8]` @ `0x6F553762` — точный поток см. чек-лист C.2. P3 безопасен
   при любой семантике гейта.)

### B.4 Противоречие v1 по +0x610

v1 называет `+0x610` одновременно «флагом IsReplaySession» и «localPlayerSlot».
Факты: `sub_6F53F160`: `cmp [ecx+0x610],1; sete al`; `sub_6F54D970` сравнивает
`+0x610` с номером слота. Это ОДНО поле, используемое двумя способами — семантику
надо дешифровать (чек-лист C.1) ДО того, как dll/сервер начнут на неё опираться.

### B.5 Чего не хватало v1 (добавлено в план)

1. **RandomSeed**: при rejoin-join сервер обязан отдать ИДЕНТИЧНЫЙ seed игры
   (иначе «бит-в-бит» из v1 ложь). Тест обязателен.
2. **Токен реконнекта**: у нового процесса нет `pid/reconnect_key`. Сервер отдаёт
   ключ клиенту (например, в GPS INIT / отдельным фреймом), .dll сохраняет в файл
   рядом с war3.exe; при rejoin шлёт `ReconnectReq{pid, key, mode:FULL, last_packet:0}`.
3. **Блэст истории при JOIN**: сервер вываливает ВСЮ историю сразу после accept,
   пока клиент грузит карту (сеть исчезает из уравнения; TCP сам буферизует).
4. **Восстановление скорости** после catch-up (см. B.3.3).
5. **Замер цены тёрна** на реальном war3 (v1: «0.05-0.1ms» — недоказано).

## D. СЕРВЕРНАЯ ЧАСТЬ (ghostrs)

### S1. Полная история пакетов (новое, `spectre-engine`)

- Новый `FullHistory` рядом с `GProxyBuffer`: полный лог broadcast-пакетов игры
  (без вытеснения). 60 мин ≈ 144k пакетов ≈ 5-30 МБ — держим в RAM, cap 90 мин.
- Пишем те же `Bytes`, что уходят в `broadcast()` (байт-в-байт живой эфир — CRC уже
  валидна; конвертер из .w3g НЕ нужен в основном пути).
- Отдача по индексу: `replay_from_full(last)` — вся история с нуля.

### S2. Join-в-начатую-игру (state machine, `spectre-engine`)

- Отдельный путь от `handle_gps_reconnect` (тот остаётся для живых клиентов):
  детект «FULL rejoin»: join в начатую игру + GPS-фрейм AUTH `{pid, reconnect_key,
  mode:FULL}`.
- Флоу: REQJOIN → проверка токена (неверный → reject, как в GPS) → слот игрока
  остаётся ИСХОДНЫМ (playing, не observer) → SLOTINFO, MAPCHECK, COUNTDOWN → START
  → НЕ ждать loading screen остальных (они в игре) → блэст истории 0..N → live.
- Обновить `conn_id/link/disconnected_since/left` (как в `handle_gps_reconnect`).
- Остальным игрокам — ничего (слоты не меняются; chat-notice по желанию).
- RandomSeed в GAMEINFO/STARTINFO — из исходных данных игры (тест на идентичность).

### S3. Токен

- Сервер: отправляет клиенту `pid`+`reconnect_key` при выдаче GPS INIT (или отдельным
  фреймом). Формат файла на клиенте согласовать с K3.

### S4. Тесты (`gproxy.rs`/новый `full_rejoin.rs`, по стилю существующих)

- история отдаётся по порядку и байт-в-байт совпадает с живым эфиром;
- join-in-progress: полный флоу фреймов (SLOTINFO→…→START→история→live);
- неверный токен → отказ; верный после таймаута (>180s) → отказ;
- seed идентичен исходному; существующие GPS-тесты зелёные (регрессии нет).

## H. РИСКИ / ОТКАТЫ

- Патчи за конфигом; P3 снимать после catch-up; любое несовпадение байт-сигнатур
  → abort патча (другая версия dll).
- C.1/C.2/C.3 могут изменить план: если state 6 — легальный skip, catch-up станет
  почти мгновенным; если +0x610 — флаг реплея, не писать его никогда.
- FullHistory: cap по времени/памяти (90 мин), иначе долгая игра = рост RAM.
- Если замер C.6 покажет >1ms/тёрн в поздней игре — принять как данность
  (60 мин ≈ 2-3 мин промотки? нет: 144k × 1ms = 144s — тогда reconsider cap/NUM
  и профилировать симуляцию; это единственный сценарий, где v1-цель «2-3s» недостижима).
